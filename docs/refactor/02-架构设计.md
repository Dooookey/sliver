## 3. 线程与事件模型（替代 goroutine）

Go 侧大量依赖 goroutine + channel；C 侧采用**固定线程集 + 队列**，映射如下：

| Go 结构 | C 侧对应 | 说明 |
|---|---|---|
| `connection.Send chan` | `outq`（有界环形队列 + mutex/cond） | 生产者非阻塞投递，10s 超时丢弃 |
| `connection.Recv chan` | `inq`（无界链表 + cond，带容量保护） | 单读者 |
| `go handler(...)` | 任务池（4~8 线程，可配置） | 任务带 `cancel_flag` 指针，连接失效即置位 |
| `time.Ticker`（ping） | 定时器轮（单线程，1s tick，最大 120s 精度够用） | 避免每连接一个 timer 线程 |
| `connection.Done()` | `atomic_bool closed` + cond broadcast | 所有等待点同时解阻塞 |
| `yamux.Session.Open/Accept` | 每连接 1 个读线程 + N 个写线程（发送信号量 64） | 与 Go 侧并发配额对齐 |
| `sync.Once` | `INIT_ONCE` / `pthread_once` | cleanup、lifecycle |

线程清单（session 模式，单连接）：读线程 1 + 写线程 ≤64（由信号量限制的实际并发）+ 任务池 4~8 + 定时器 1 + 主循环 1。
每个任务线程必须可被 `connection closed` 打断（socket 关闭 + `cancel_flag`）。

**关键不变量**（照抄 Go 语义，否则 server 断连）：
1. 一条 Envelope 一条 yamux stream，写完即关；
2. 同一 tunnel id 的 `Sequence` 由单写者递增，且在「入队成功」后才 +1；
3. `Send` 队列在连接失效后**不关闭**，写线程靠 `closed` 标志退出（对应 `transports/session.go:87-119` 的双重 select）；
4. beacon 的 check-in 严格串行，不重叠（`runner.go:295-321`）。

## 4. 内存、错误与日志

- **分配**：所有长生命周期对象（config、密钥、连接、隧道）用 `malloc` 包装；单条消息用 **arena**（`arena_t`，按消息释放），避免碎片与泄漏。
- **上限**：Envelope ≤512MiB（与 Go 一致，`transports/mtls/mtls.go:65`），实际内建更严的软上限（默认 8MiB，可配置），隧道帧 ≤64KiB，DNS 单包 ≤255B（AAAA 通道）。
- **错误**：统一 `sliver_err_t`（int 码 + 上下文串），**不抛异常**（`-fno-exceptions`）；错误分级 `RETRY / FATAL_CONN / FATAL_PROC` 直接影响主循环的重连/退出。
- **日志**：`LOG_DEBUG/INFO/WARN/ERROR`；Release 编译时 `LOG_DEBUG` 编译为空，且**不回显配置内容**（对应 Go 侧 `{{if .Config.Debug}}` 把错误文本清空的技巧，如 `dnsclient/dnsclient.go:77-80`）。
- **敏感数据**：密钥、证书、C2 URL 只存在于 `implant_secrets.c`（单 TU），运行期按需解密到堆，`mlock`（可用时）+ 退出清零。

## 5. 传输实现策略

### 5.1 mtls（M1，第一优先）

```
tcp_connect → TLS1.3(客户端证书, 只验CA链) → send "MUX/1" → yamux_client
  ├─ 写线程：从 outq 取 Envelope → open stream(SYN) → write frame → FIN
  └─ 读线程：accept stream → read frame → inq
```

- TLS：**mbedTLS 3.6**（`MBEDTLS_SSL_PROTO_TLS1_3`，仅 client、无 ALPN）+ 自定义 verify 回调实现「只验链到内置 CA、跳过主机名」（体积原因不用 OpenSSL，见 §6）。
- 必须支持 P-521/P-384/P-256 客户端证书（build 期随机曲线，见 01 §3.2）。
- yamux：按 `vendor/github.com/hashicorp/yamux` 移植：`SYN/ACK/FIN/RST` 标志、window update、ping、goaway、stream 状态机；只实现 client 侧即可（server 是 yamux server）。

### 5.2 http(s)（M3）

- 自研 HTTP/1.1 客户端（不引 libcurl：需要精确控制 header 顺序/随机 path/cookie 语义，且要能取消未完成 GET）。
- 组件：`http_conn`（连接/重连）、`cookie_jar`（全收全发）、`nonce_gen`（数字串 + 噪声字符）、`encoder`（5 种内置 + gzip）。
- 会话建立、轮询（200/204/403）、发送（202）、关闭（202）严格按 01 §3.3。
- 可选：Windows 下 WinINet 驱动（对齐 Go 的 `driver=wininet`），一期不做，接口预留。

### 5.3 dns（M4）

- 自带 DNS 报文构造/解析（避免依赖 ldns 的构建负担）：查询 A/TXT/AAAA，**必须能改写 TTL**（AAAA 元数据通道）。
- resolver 发现：Linux 读 `/etc/resolv.conf`；Windows 用 `GetAdaptersAddresses`（与 Go 侧一致，`dnsclient/conf_windows.go:49-137`）。
- 分片/manifest/并行拉取按 01 §3.4；并发 worker 数默认 `2 × resolvers`。

### 5.4 pivot / rportfwd / socks（M4）

- pivot 帧与双层加密按 01 §3.5；`PivotHello` 的 minisign 文本签名校验复用 `crypto/minisign.c`。
- rportfwd：implant 监听 → 每条入站连接建反向隧道（`CreateReverse` + `Rportfwd{}` 标记），帧内带 `AuthorizationID`。
- socks5：隧道池 + 流控 v1（`SocksData.Ack/Sequence`），ack 纯控制帧不得创建隧道。

### 5.5 WireGuard（M5，单独立项）

三个选项，推荐 **B**：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A. 内核 WG + 系统 TUN | Linux 用内核 wireguard 模块 + TUN 设备路由 | 需要 root/CAP_NET_ADMIN，Windows 需装 WireGuard 驱动 | 与「无特权植入」目标冲突 |
| B. 用户态 WG + 轻量 TCP/IP 栈 | 移植 Noise IK（boringtun 风格，C 重写约 3k 行）+ lwIP/picoTCP 提供 socket | 3~5 周 | 协议细节多（Noise_IKpsk2、cookie、rekey） |
| C. 复用 wireguard-go + gVisor（cgo） | 把 Go 代码编成静态库链进 C | 破坏「纯 C/C++」目标，体积 +8MB | 与重构初衷冲突 |

结论：M5 之前不排期；若必须支持 `wg://`，先做 B 的 PoC（单 peer、单 TCP 流、无 rekey），验证后再产品化。

## 6. 加密层实现（v2：为体积换底座）

**结论先行**：产品构建**不用 OpenSSL**。OpenSSL 3 静态链接 1.5–3 MB，直接顶穿「KB 级」预算；
它只作为开发期的对拍/参考实现（`IMPLANT_CRYPTO_BACKEND=openssl` 可选编译，仅用于生成金标向量与排查）。

| 原语 | 产品实现 | 备注 |
|---|---|---|
| TLS 1.3 客户端 | **mbedTLS 3.6 LTS**（`MBEDTLS_SSL_PROTO_TLS1_3`），仅 client 角色、无 ALPN | 需支持 ECDSA P-256/384/521 客户端证书（build 期随机曲线），自定义 verify 回调实现「只验 CA 链、跳过主机名」 |
| X25519 | mbedTLS `mbedtls_ecdh`（Curve25519） | age 收发 |
| ChaCha20-Poly1305 | mbedTLS `mbedtls_chachapoly` | 信封 AEAD，nonce12/tag16/AAD 空 |
| AES-128/256-GCM | mbedTLS `mbedtls_gcm` | TLS1.3 协商用（Go server 默认套件可能选 AES） |
| SHA-256 / HMAC / HKDF | mbedTLS `mbedtls_sha256`、`mbedtls_md_hmac`、`mbedtls_hkdf` | age 需要精确 salt/info |
| Ed25519（签名/验签） | **monocypher** `crypto_eddsa_*` | 信封签名、minisign raw 验签；mbedTLS 3.x 的 EdDSA 依赖 PSA，接口与体积都更重 |
| BLAKE2b（32/64 输出） | **monocypher** `crypto_blake2b_generic` | keyID 需要 32 字节参数化输出（OpenSSL 只有 512） |
| gzip | **miniz**（单文件，inflate+deflate） | 只要求合法 gzip，不要求字节一致 |
| base64 raw/std、base32 自定义、hex | 自写（约 150 行） | 字母表见 01 §3.3/§3.4 |
| bech32 | 自写（约 80 行） | age 密钥串解析，非 bech32m |
| CSPRNG | mbedTLS `mbedtls_ctr_drbg` + 平台熵源 | Windows `BCryptGenRandom` / Linux `getrandom` |

**mbedTLS 裁剪**（`configs/sliver_implant_config.h`，通过 `MBEDTLS_CONFIG_FILE` 注入）：
只保留 TLS1.3 client、X25519、secp256r1/384r1/521r1、AES-GCM、ChaCha20-Poly1305、SHA-256/512、HKDF、X.509 解析（不写）、CTR-DRBG；
关闭 TLS1.2、DTLS、PSK、session ticket、renegotiation、server 模式、PKCS#1 v1.5 写、错误字符串表（`MBEDTLS_ERROR_C` off）、`MBEDTLS_SELF_TEST`。
实测参考：同等最小配置下 mTLS 能力在 Cortex-M33 约 70 KB（见 wolfSSL 2026 基准），x86_64 静态预计 200–400 KB。

**age 实现要点**（逐字节，01 §4.1）：
1. `eph_sk` 随机 32B → `eph_pk`；`ss = X25519(eph_sk, recipient_pk)`；
2. `wrapKey = HKDF-SHA256(ikm=ss, salt=eph_pk‖recipient_pk, info="age-encryption.org/v1/X25519", L=32)`；
3. `fileKey` 16B 随机；`body = ChaCha20Poly1305(wrapKey).Seal(nonce=0×12, aad="", fileKey)`；
4. 头：`"age-encryption.org/v1\n-> X25519 "` + `base64raw(eph_pk)` + `"\n"` + `base64raw(body)` + `"\n--- " + base64raw(headerMAC) + "\n"`；
5. `streamKey = HKDF-SHA256(ikm=fileKey, salt=nonce16, info="payload", L=32)`；分块 64KiB，nonce=`[0,0,0][u64 BE idx][flag]`，末块 flag=0x01；
6. Sliver 特有：**输出前裁掉 32 字节固定前缀**，解密前补回。

## 7. protobuf 方案（自研 codegen）

**为什么不用 nanopb/protobuf-c**：需要与 Go 生成的字段号严格一致、只覆盖用到的消息子集、要能把「默认值省略」和 `int64` 负数处理好，并且要能顺手产出金标向量。

**流程**：

```
protobuf/sliverpb/sliver.proto ─┐
protobuf/commonpb/common.proto  ├─ tools/codegen/gen_c.py ─→ src/proto/generated/*.{h,c}
protobuf/dnspb/dns.proto       ─┘                              + tests/vectors/schema.json
```

- 输入：**白名单消息**（`Envelope`、`Register`、`BeaconRegister`、`BeaconTasks`、`Ping`、`commonpb.Request/Response/Process/File`、文件/进程/执行/隧道相关 req/resp，按 01 §8 的 P0/P1 逐步扩）。
- 生成：`struct` + `encode_<msg>()`/`decode_<msg>()` + `free_<msg>()`；`bytes`/`string` 用 `(ptr,len)` 二元组，`repeated` 用 `(ptr,count,cap)`。
- 运行时：`varint`/`zigzag`? （proto3 `int64` 是 varint 二补码，负数 10 字节，**不用 zigzag**）、`length-delimited` 读写、跳过未知字段（必须实现，server 未来加字段不能崩）。
- `map<k,v>`：仅 `Grep.Results` 用到 → P2 再生成（用 `repeated entry` 模拟）。
- 一致性保障：codegen 同时输出 `schema.json`（字段号+类型），C 侧单测断言「我们的字段号 == 从 Go `*.pb.go` 解析出的字段号」。

## 8. 配置注入（替代 Go 模板）

**两层产物**，全部由 CMake 在 configure 阶段从 `config.json` 生成（实现见 `cmake/SliverConfigGen.cmake`）：

| 产物 | 内容 | 谁能 include |
|---|---|---|
| `implant_build_config.h` | 开关（`SLIVER_FEATURE_*`）、数值常量（interval/jitter/reconnect/max-errors/poll-timeout）、`SLIVER_IS_BEACON`、limits、`SLIVER_C2_COUNT`、`SLIVER_SECRET_COUNT` | 全工程 |
| `implant_secrets.c` | `sliver_c2_urls[]`、`sliver_secret_values[]`（11 个密钥槽：age 密钥/证书/WG）、name/build_id | 只被 `src/core/config.c` 链接 |

**槽位一致性**：`sliver_secret_id_t`（`include/sliver/config.h`）与生成顺序绑定，`sliver_config_self_check()` 断言
`SLIVER_SECRET_COUNT == sliver_secret_value_count`，生成器加字段而 C 侧忘改会立刻失败。

**随机种子**：每次 configure 生成新的 `SLIVER_BUILD_SEED`，参与 secrets 的 XOR key 与 UA/nonce 派生 → 同参数两次构建产物不同
（等价 garble `-seed=random`）。

**与 server 的契约**（`server/cppbuild` + `server/rpc/rpc-generate-cpp.go`，详见 [06](06-GenerateCpp改造方案.md)）：

```
GenerateCpp(req) → 镜像 Generate：
  1. 复用 generate.GenerateConfig 生成 ImplantBuild（密钥/证书/WG）
  2. 复用 db.LoadHTTPC2ConfigByName 取 HTTP profile
  3. cppbuild 写 <slivers>/<os>/<arch>/<name>/config.json
  4. cmake -S implant-cpp -B <buildDir>/build -DSLIVER_CONFIG_JSON=... -DIMPLANT_FORMAT=...
     cmake --build <buildDir>/build --config Release
  5. cppbuild 收集产物到 <buildDir>/bin/<name><ext>，并校验 PE/ELF + 静态性 + 体积
  6. generate.ImplantBuildSave(...) 落库（必须先于返回，否则 server 不认回连）
  7. 返回 clientpb.Generate{File, ImplantBuildID, ImplantName}
```

失败处理：cmake 命令 + 最后 4 KB 输出进服务端日志，客户端收到 `cppbuild: cmake ...` 的错误；静态性/体积不达标同样是**硬失败**。

## 10. 代码规范与质量门禁

- 语言：**C11**（核心/协议/加密）+ 少量 **C++17** 仅限 Windows 注入相关（`no exceptions / no RTTI`，`/EHs-c- /GR-`）。
- 命名：`sliver_` 前缀内部符号；`SLIVER_` 宏；`static` 化所有非导出符号 + `-fvisibility=hidden`。
- 告警：MSVC `/W4 /WX`（关闭 4100/4189 等噪声），GCC/Clang `-Wall -Wextra -Werror -Wconversion`（逐步收紧）。
- 静态检查：clang-tidy（`bugprone-*`、`cert-*` 子集）+ cppcheck；CI 只对新增改动卡门禁（避免历史噪音）。
- 单测：`ctest`；金标向量必须双端（Go 生成 → C 校验，C 生成 → Go 校验）。
- Fuzz：`libFuzzer` 覆盖 `proto decode`、`yamux frame`、`envelope read`（M1 起进 CI 的 nightly）。

## 11. 与现有 Go 行为的对齐清单（Code Review 用）

1. `Envelope.ID` 必须 `int64` 且允许负数；应答回填同 ID、`Type` 保持 0。
2. 未知类型回 `UnknownMessageType`。
3. `MsgPing` 只发不收；`Register` 无回执。
4. beacon 带结果不 Recv；`NextCheckin` 秒；interval/jitter 编译期单位 ns。
5. 隧道：`Sequence` 递增、≤64KiB、关闭语义按 Capabilities、IDA 不复用（随机 uint64）。
6. Windows：每个任务前后 impersonate/revert（P4）。
7. 重连固定 60s，无指数退避；错误计数到 1000 退出。
8. HTTP：cookie 全收全发；nonce 选择 encoder；403 视为会话失效。

> §9 表里的期次按 [04](04-里程碑与验收.md) 的 P0–P5 阅读（M0=skeleton、M1→P0、M2→P1、M6→P4）。

## 12. 体积与静态链接策略（v2 硬约束）

### 12.1 预算

| 目标 | 字节 | 触发行为 |
|---|---|---|
| 硬上限 | 5 MiB | `cppbuild.ValidateArtifact` 直接失败 |

### 12.2 静态链接矩阵

| 平台 | 编译/链接 | 产物验证 |
|---|---|---|
| Windows / MSVC | `/MT`（`CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`）+ `/GL /LTCG` + `/OPT:REF /OPT:ICF` | `dumpbin /dependents` 无 `VCRUNTIME140/ucrtbase` |
| Windows / MinGW | `-static-libgcc -static-libstdc++`，**不加 `-static`**（否则 `-shared` 会产出 ar 归档） | 同上 + `objdump -p` 无 `libgcc_s_*/libwinpthread` |
| Linux | `-static`（优先 musl-gcc / zig cc；glibc 静态可用但体积大） | `readelf -l` 无 `PT_INTERP` |

### 12.3 体积手段（按收益排序）

1. **换掉 OpenSSL**（最大项，1.5–3 MB → mbedTLS 200–400 KB）；
2. 关掉 `MBEDTLS_ERROR_C`（错误字符串表可观）、只编需要的曲线/套件；
3. `-ffunction-sections -fdata-sections -Wl,--gc-sections` + `-flto` + `-s`；
4. 不用 `stdio` 的格式化大件（`printf` 家族），核心日志用自写小格式化；
5. PE 侧 `/OPT:REF /OPT:ICF`、`/Gy /Gw`，去掉 `__FILE__` 断言；
6. 静态库里只链接用到的 `.o`（CMake 静态库默认行为，注意别用 `--whole-archive`）。
