5. **底层框架有 3 类 P0 级稳定性问题，本次已修 2 类**：
   - 线程对象所有权错误：trampoline 在 `join`/`detach` 之前 `free(t)` → 每次会话 teardown（join 心跳线程）与每个短命 worker（detach）都是 UAF（**已修**）；
   - portfwd socket 双重释放 + 会话线程无锁读写 `f->sock`（**已修**）；
   - 单读者 yamux 模型：会话线程在同步 handler 里忙时无人回 PING ACK，超过服务端 keepalive（10 s 写超时 / 30 s ping）即被判定掉线（**未修，需引入专用泵线程，见 §6**）。
6. **可扩展性**：新增一条同步命令 = 5 文件 6 处；异步命令 = 9–11 处；新增一种隧道 = 12–15 处（必须复制 shell/portfwd 整套"数组+私有锁+sender+teardown"）；新增一种传输 = 13–16 处（`session.c` 里 TLS/yamux/frame 硬编码 30 行，没有接缝）。建议按 §7 的三张表（dispatch X-macro、`tunnel_ops`、`transport_ops`）改造。

## 4. 底层框架稳定性

### 4.1 线程与所有权

| 线程 | 创建 | 收尾 | 结论 |
|---|---|---|---|
| 会话读线程 | `session.c:263` | 同线程返回 | 正常 |
| 心跳线程 | `session.c:260` | join | **此前 UAF（trampoline 先 free）** |
| shell 读线程 | `shell.c:407` | detach + 自收尾 | 同上 |
| portfwd relay | `portfwd.c:317/346` | detach + 自收尾 | 同上 + socket 双释放 |
| execute / file worker | `dispatch.c:396/608` | detach | 同上 |

**根因**：`sliver_thread_t` 由 trampoline 独占 `free`，而 `join()` 仍读 `t->handle`（`win32/thread.c:105`）、`detach()` 仍写 `t->handle`（`:117-118`）。短命 worker（chmod 等）几乎必然踩中。

**修复**：改为引用计数（creator + trampoline 各持一份），trampoline 先拷贝 `fn/arg` 再执行，最后一个引用负责释放；`join` 用 creator 的引用等待句柄后释放。

### 4.2 共享状态与锁

| 对象 | 守护 | 风险 |
|---|---|---|
| `static session_tx_t tx` + `g_tx` | `tx_lock` + `closed` | 跨会话代际缺失：旧 worker 可把响应写进**新会话**（用新 signer），服务端按 ID 丢弃，但语义已错 |
| `g_rpc_send` / `g_send` | 无锁函数指针 | 同上，teardown 不清空 |
| `g_tunnels[8]` / `g_forwards[8]` | 部分加锁 | `tunnel_find`/`forward_find` 无锁遍历，worker 在锁内 `memset` 整槽 → 旧隧道帧写进新隧道 |
| yamux `streams[]` | `streams_lock`，锁序 `tx → pump → streams → write` | 锁序自洽无环；但 pump 持锁做 100 ms TLS 读、write 持锁做阻塞写 |
| DRBG（`crypto_mbedtls.c:15`） | 无锁，且未开 `MBEDTLS_THREADING_C` | 当前只在会话线程串行使用，属潜伏风险 |
| `log` | debug 构建有锁 | `close_file` 无锁；DLL 形态从不 `log_init` |

### 4.3 传输与 yamux 协议偏差（本次已修 4 项）

| 项 | 原状 | 影响 | 处理 |
|---|---|---|---|
| FIN/RST 承载帧 | 只在 DATA 分支处理 FIN，完全不处理 RST；自己把 FIN 发在 DATA 帧上 | Go 的 `stream.Close()` 发 `windowUpdate+FIN`，C 端 `fin_received` 永不为真 → EOF 分支成死代码，RST 不可见 | **已修**：两条分支都处理 FIN/RST，FIN 改发 `windowUpdate`（与 `stream.sendClose` 一致） |
| SYN 窗口语义 | SYN 帧 `length` 携带 256 KiB | Go 的 `incrSendWindow` 会**累加**该值 → 对端发送窗口被抬到 512 KiB，而 C 只缓冲 512 KiB 且超限 RST → 大响应可能被丢 | **已修**：SYN `length=0`（与 `sendWindowUpdate` 的 delta=0 一致） |
| 自有流 ACK 判定 | `local_ids` 只写不读 | 槽位释放后收到自己流的 SYN-ACK 会被当成"对端新流"并回 ACK → Go 判 duplicate stream 并发 `goAway(protoErr)` **关闭整条会话** | **已修**：`local_ids` 参与判定，命中即视为 ACK |
| accept 单槽 | `pending_accept` 标量 | 会话线程忙时服务端连开两条流，第一条被覆盖 → 请求永久丢失（Go 的 backlog 是 256） | **已修**：改为 32 槽环形队列，满则 RST |
| 半帧超时 | `io_read_full` 读到半帧再超时即置 `failed` | 一次 100 ms 接收超时就能判死会话（与"短超时放行写者"的设计直接矛盾） | **已修**：帧头跨调用续读（`hdr_buf/hdr_got`），帧体给 30 s 预算 |
| `bio_recv` 错误分类 | 所有 socket 错误映射成 `WANT_READ` | RST/半开链路永不检测 → `accept` 2 ms 空转、会话永不退出、重连永不触发 | **已修**：`-2`=超时→WANT_READ，其余→`MBEDTLS_ERR_NET_RECV_FAILED` |
| 发送超时 | 只有 `SO_RCVTIMEO`，`io_write_full` 注释里的"5 s"不存在 | 阻塞 `send()` 可无限挂住，而它持有 `tx_lock/write_lock/pump_lock` → 整条发送链死锁 | **已修**：新增 `sliver_socket_set_send_timeout()`（TLS/portfwd 各按需设置）+ `io_write_full` 仍保留 5 s 重试上限 |
| TLS 写时排空丢数据 | `sliver_tls_write` 在 `WANT_READ` 时 `mbedtls_ssl_read` 到 scratch 后**丢弃** | 排空到应用数据（一整个 yamux 帧）会让流解析彻底错位 | **已修**：新增 `pending` 缓冲，`sliver_tls_read` 优先交付 |
| 握手无总超时 | `WANT_READ` 永久循环 | 对端 accept 后不说话 → `MaxConnectionErrors` 永不生效 | **已修**：30 s 握手超时 |

### 4.4 入口与产物形态

| 项 | 状态 |
|---|---|
| `main.c` 配置缺失返回 0 | **已修**：返回 3（`run_from_build_config` 的 `-1` 不再被吞） |

## 7. 扩展性评估（"未来扩展的稳定性"）

### 7.1 新增一条命令

| 场景 | 文件 | 触点 |
|---|---|---|
| 纯编解码 | 3 | 5（`proto.h` 常量+声明、`proto.c` 编+解、`dispatch.c` handler+表项） |
| 带平台实现 | 5–6 | 7–9（+win32/posix 各 1–2、+域头文件） |
| 异步/隧道 | 6–8 | 10–14（+worker 骨架、+`CMakeLists.txt` 登记新源文件） |

**易错点**（本次审计全部命中过至少一次）：`resp_type` 的"0=空响应/自答"约定；proto3 省略默认值导致客户端"看不到"字段（`ReadFiles`）；id 必须从 `constants.go` 数 iota（`49/129/134/87/136` 没有独立响应常量）；`sliver_reader_string` 超长即失败会把路径错误变成"unknown message type"；repeated 数组超限必须 return -1 而不是静默丢弃；handler 在读线程内执行必须考虑 keepalive。

### 7.2 新增一种隧道（socks5 / rportfwd）

12–15 处，且必须复制 shell/portfwd 的"8 槽数组 + 私有懒锁 + sender + teardown 两行"。建议抽出 `tunnel_ops`：

```c
typedef struct {
  const char *name;
  int (*data)(const sliver_tunnel_data_t *td);   /* 返回 1 = 已处理 */
  int (*close)(uint64_t tunnel_id);
  void (*shutdown)(void);
} sliver_tunnel_ops_t;
```
`sender` 改为带会话代际的上下文对象，`teardown` 由注册表统一遍历，新隧道只需实现 3 个回调 + 注册一行。

### 7.3 新增一种传输（HTTP/DNS/WG）

13–16 处，核心障碍是 `sliver_session_run` 把 TLS/MUX1/yamux/frame/心跳/accept/teardown 六件事写在一个函数里。建议：

```c
typedef struct {
  int  (*connect)(void **ctx, const sliver_session_config_t *cfg, char *err, size_t err_len);
  long (*read)(void *ctx, void *buf, size_t len);    /* -2 = 暂无数据 */
  long (*write)(void *ctx, const void *buf, size_t len);
  void (*close)(void *ctx);
} sliver_transport_ops_t;
```
配合 `config.c` 已有的 `feature_http/dns/wg` 开关（目前只打印）与 `main.c` 的 `mtls://` 硬解析改为按 scheme 分派。

### 7.4 分派表与错误语义

`g_handlers` 是手维护线性表，`proto.h` 与 `dispatch.c` 各存一份 id（还有一堆裸数字）。建议 X-macro 单一来源：

```c
#define SLIVER_RPC_TABLE(X) \
  X(LS,   5, 6, sliver_rpc_handle_ls) \
  X(PWD, 12,13, sliver_rpc_handle_pwd) ...
```
同时把 handler 的三态 `int`（-2/0/其他）改成枚举 `SLIVER_RPC_REPLIED / SLIVER_RPC_OK / SLIVER_RPC_ERROR`，失败时回一个带 `Response.Err` 的语义化响应，而不是 `UnknownMessageType`。
