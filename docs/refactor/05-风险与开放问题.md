# 05 风险与开放问题

---

## 1. 兼容性风险（最高优先级）

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | 逐字节契约写错（age 头 32B 裁剪、HKDF salt/info、BLAKE2b 输出长度、u32 LE 长度、签名 74B 字段序） | 握手被拒，且 server 侧错误信息极少（如 HTTP 一律 `ErrDecryptFailed`） | M0 就把金标向量建立起来；每处敏感常量集中在一个 `protocol_const.h`，附来源注释 |
| R2 | TLS 1.3 参数不匹配（server 强制 1.3、客户端证书曲线可能是 P-521、无 ALPN） | 握手失败 | OpenSSL 显式 `set_min_proto_version(TLS1_3)`、不设 ALPN、`set1_groups` 保持默认（含 P-521）；M1 用三种曲线各生成一次 build 验证 |
| R3 | yamux 流控实现偏差（window update、SYN/ACK、keepalive） | 大消息卡死或连接被 reset | 移植而非重写；用 Go 侧 yamux 做对拍（起一个 Go yamux server 单测，喂 C 侧帧） |
| R4 | protobuf 默认值/未知字段处理 | server 升级加字段后 C 侧解析崩 | 强制实现「跳过未知字段」，且所有字段可选；codegen 输出字段号断言 |
| R5 | `Envelope.ID` 用无符号导致负 ID 回错 | 响应丢失、60s 超时 | 类型固定 `int64_t`；单测覆盖负数 ID |
| R6 | beacon 「带结果不 Recv」语义写错 | server 侧任务状态错乱 / 连接被占死 | 直接照抄 `runner.go:367-372` 的分支结构，单测覆盖 |
| R7 | 隧道序号/关闭语义（`Sequence=0` vs `>0`、Capabilities） | server 10s 后强拆隧道 | 先声明保守 Capabilities（不带 `TUNNEL_TERMINAL_V1`），M4 再开新语义 |

## 2. 许可与合规

| 组件 | 许可 | 与 Sliver(GPLv3) 兼容 | 结论 |
|---|---|---|---|
| OpenSSL 3.x | Apache-2.0 | 是 | 主选 |
| libsodium | ISC | 是 | 主选（BLAKE2b 参数化输出） |
| zlib | zlib | 是 | 主选 |
| mbedTLS | Apache-2.0 | 是 | **不选**：3.x 不支持 TLS 1.3 |
| wolfSSL | GPLv2-only / 商业 | **否**（GPLv2-only 与 GPLv3 冲突） | 排除，除非有商业授权 |
| BoringSSL | OpenSSL+ISC | 是 | 备选（构建成本高，且无 BLAKE2b） |
| hashicorp/yamux（仅参考协议） | MPL-2.0 | 仅参考协议、不复制代码 | 自行实现 |

**结论**：C implant 整体按 **GPLv3** 发布（与 Sliver 一致），依赖只用上表「是」的组合。

## 3. 工程风险

| # | 风险 | 对策 |
|---|---|---|
| E1 | 线程模型迁移引入竞态（Go channel 语义 vs 有界队列） | 统一 `conn_generation` 代际号 + `closed` 原子标志；所有等待点可被打断；TSan 进 CI |
| E2 | PTY / 文件打包（tar+gzip）/ 大文件分块被低估 | M2 单独留 3 人日；先用「小文件 + 简单命令」打通，再补 tar/PTY |
| E3 | 体积与指纹（静态链接 OpenSSL 体积 2~4MB） | `IMPLANT_LTO`、`--gc-sections`、只编所需算法；M6 做体积预算（目标 ≤3MB exe） |
| E4 | 与上游 Sliver 版本漂移（协议常量变化） | 固定 submodule/commit；升级时先跑金标向量 + 字段号断言，再改代码 |
| E5 | server 侧 `GenerateCpp` 与官方 `Generate` 分叉 | 抽公共函数（config 组装、落库），只在「构建后端」分叉；避免两套逻辑各自演化 |
| E6 | WSL 构建从 Windows 调起的 PATH/代理告警 | 统一 `wsl --exec env -u PATH bash -lc`；CI 里用原生 ubuntu runner |
| E7 | 调试困难（implant 崩了没有栈） | Debug 预设保留符号 + 可选 minidump（Windows）/ core（Linux）；日志分级 |

## 4. Sliver 工程本身的空白（我们顺手补上）

| 空白 | 现状 | C 侧做法 |
|---|---|---|
| 混淆有效性没有断言 | server 不做 `strings`/符号检查（`server/generate` 无 objdump/readelf 引用） | CI `artifact-hygiene` job：断言无绝对路径/关键字、两次构建 sha256 不同 |
| 配置注入正确性没有测试 | 只有 zip/header 级测试 | 生成头/secrets 与输入 JSON 逐字段比对单测 |
| 协议无版本号 | Envelope 无版本字段 | 金标向量 + 字段号断言作为事实上的「协议版本」 |
| 传输层单测薄 | 只有 `connection_test.go`、`tunnel_test.go` 等少量 | C 侧对 yamux/frame/age 做 fuzz + 对拍 |

## 5. 待你拍板的开放问题

1. **产物形态优先级**：一期是否只做 `exe`（Win+Linux）+ `dll/so`，shellcode 通过外置转换器（donut 等价物）另做？
2. **传输优先级**：确认「mtls → http → dns → pivot → wg」这个顺序，还是必须先有 `wg`（若必须，需接受 M5 提前并增加 20 人日）？
3. **语言边界**：核心协议/加密用纯 C11，仅 Windows 注入部分用 C++17 —— 是否接受？
4. **依赖引入方式**：libsodium 用 `third_party` submodule 静态编（体积可控），还是 Windows 走 vcpkg、Linux 走 apt（构建简单但版本不可控）？
5. **server 侧改造范围**：`GenerateCpp` 是否允许改动 `services.proto` 之外的 server 代码（如抽公共函数、加构建缓存）？
6. **CI 归属**：CI 是放 GitHub Actions（需要仓库权限与 runner 成本），还是本地 `scripts/matrix.ps1` + 手动触发？
7. **是否保留 Go implant 作为对拍基准**：建议保留（`implant/` 不动），CI 里跑「同配置双产物」对比。
8. **M6 的注入/CLR/BOF 是否在本期**：这三项工作量接近 M1+M2 之和，建议单独立项。
